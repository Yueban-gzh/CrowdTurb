## 3. A-local v0.2 可调整对象

### 3.1 出口

| 项目 | 当前支持 |
| --- | --- |
| ID | `exits[].id`，如 `E1` |
| 定位 | `side`（N/S/E/W）+ `offset`（米） |
| 候选可调参数 | 仅 `width`（米） |
| 范围 | 正数；若声明 `exit_width`，还必须满足 `allowed_range` |
| 位置移动 | `apply_layout()` 不支持；需要新建/编辑场景 |
| 增加/删除出口 | 编辑器可作为场景结构编辑；不属于 D 的当前候选变量 |
| 离散约束 | 至少形成一个出口格；不得贴墙角、同侧重叠或被设施覆盖 |

### 3.2 可移动设施

第一版推荐使用固定尺寸、不可穿越的旋转矩形临时展台。

| 字段 | 含义 | 修改权限 |
| --- | --- | --- |
| `id` | 稳定对象 ID，如 `F1` | 不修改 |
| `center` | 中心 `[x,y]`，米 | 需要 `movable=true` |
| `rotation_deg` | 绕中心逆时针角度，度 | 需要 `movable=true` |
| `length` | 局部 x 轴长度，米 | 需要 `resizable=true` |
| `width` | 局部 y 轴宽度，米 | 需要 `resizable=true` |
| `allowed_region` | 允许放置多边形，米 | 设施矩形必须完整位于其中 |
| `size_limits` | 长宽允许范围 | `resizable=true` 时必填 |
| `effect` | 第一版仅 `block` | 不支持服务点或降速区 |

设施 ID、名称、类别和权限由 A 的场景配置确定。D 应在已声明的变量和权限内生成候选，不直接突破 `movable` / `resizable` / `size_limits`。

### 3.3 通道

当前可用 `geometry.walls` 和 `geometry.obstacles` 表达通道，并检查：

- 人群是否能到达出口；
- 设施是否切断必要通路；
- 近似最小通路宽度是否达到 `layout_policy.min_passage_width`。

当前**没有**独立的 `passage_id`，也没有“通道中心、宽度、长度、连通关系”作为 D 可直接修改的变量。若首轮优化必须包含通道，需要 A/C/D 先确认参数化方式，再升本地版本；不能把通道偷偷当作设施处理。

### 3.4 初始人群

- 人群区 `id`、多边形和 `count` 属于场景输入。
- 初始人群区是设施禁放区；设施覆盖人群格会报 error。
- 当前不支持候选重新分配人群并保持总人数。
- `profile` 可为 `seated` / `standing`，但 A 不据此生成个体，也不把它当作已完成的人群行为模型。

### 3.5 可变参数声明

顶层 `variable_parameters` 用于向 B 说明“什么参数变了”，不直接参与栅格化或求解哈希。

```json
{
  "name": "南侧主出口宽度（m）",
  "type": "exit_width",
  "target_id": "E1",
  "unit": "m",
  "allowed_range": [4.0, 10.0],
  "current_value": 6.0,
  "scene_diff": [{"exit_id": "E1", "width": 6.0}]
}
```

- 必填：`name`、`type`、`target_id`、`unit`、`allowed_range`、`current_value`。
- `scene_description` 与 `scene_diff` 必须且只能提供一个。
- 支持类型：`exit_width`、`facility_center_x`、`facility_center_y`、`facility_rotation`、`facility_length`、`facility_width`。
- 参数值当前按连续数值处理；旋转角会归一化到 `[0,360)`。是否改为离散步进由 A/D 评审后增加约束。
- 名称和 `(type,target_id)` 绑定必须唯一。
- 当前值必须与场景实际值一致，且在允许范围内。
- 候选修改后，A 自动刷新 `current_value` 和 `scene_diff`。
- 除单对象范围、允许区域和几何规则外，当前没有通用任意联合不等式描述语言。

## 4. Python 对接接口

### 4.1 加载与导出

```python
from scene_io import load_scene, validate, rasterize, export_npz

scene = load_scene("scenes/gym_facilities_example.json")
problems = validate(scene)          # [{"level": "error"|"warning", "msg": "..."}]
R = rasterize(scene)                # C 的直接输入
export_npz(scene, "scenes/output/base.npz")
```

`export_npz()` 在存在 error 级问题时抛 `RuntimeError`，不会静默导出非法场景。

### 4.2 生成候选新场景

```python
from layout_eval import apply_layout, LayoutError

new_scene = apply_layout(scene, [
    {"facility_id": "F1", "center": [22.0, 7.5]},
    {"exit_id": "E1", "width": 8.0},
])
```

- 返回深拷贝，不修改原场景。
- `meta.revision` 递增，`meta.parent_revision` 指向原修订。
- 同一候选重复修改同一对象会报错。
- 越权、未知字段、未知 ID、非法范围抛 `LayoutError`。
- 应用成功不等于几何可行，仍须 `validate()` 或 `evaluate_layout()`。

### 4.3 单个候选与批量候选

```python
from layout_eval import evaluate_layout, evaluate_candidates

one = evaluate_layout(scene, [{"facility_id": "F1", "center": [22.0, 7.5]}])

report = evaluate_candidates(scene, [
    {"candidate_id": "C1", "changes": [{"facility_id": "F1", "center": [22.0, 7.5]}]},
    {"candidate_id": "C2", "changes": [{"facility_id": "F1", "center": [22.1, 7.5]}]},
])
```

单个报告的重要字段：

| 字段 | 含义 |
| --- | --- |
| `feasible` | 没有 error 级问题；warning 不影响几何可行 |
| `problems` | 具体错误/警告 |
| `changes` | D 提交的原始修改 |
| `scene_revision` | 新场景修订号 |
| `layout` | 修改后的全部设施位姿 |
| `changed_facilities` / `changed_exits` | 实际修改对象 |
| `pose_delta` | 每个设施的位移、旋转和尺寸变化 |
| `move_distance_m` / `rotation_delta_deg` | 原始修改量，A 不做代价排序 |
| `exit_width_deltas` | 出口宽度前后差值 |
| `variable_parameters` | 修改后的声明，可给 B |
| `variable_parameter_deltas` | 每个参数的前值、后值、差值、是否变化 |
| `mask_hash` | 固定障碍+设施掩码指纹 |
| `walkable_hash` | 可行走掩码和出口几何指纹 |
| `input_hash` | 求解输入指纹 |
| `layout_hash` | 连续设施位姿指纹 |
| `mask_changed` | 障碍掩码是否改变 |
| `below_grid_resolution` | 位姿改变但被栅格吞掉 |
| `solve_required` | 批量评价中是否为新的可行输入 |
| `duplicate_of` / `duplicate_mask_of` | 重复来源 |
| `metrics` | 格数等几何统计，不是拥堵指标 |

批量去重以 `input_hash` 为准，`mask_hash` 仅作为辅助诊断。出口宽度变化可能不改变障碍掩码，但仍改变出口和可行走输入，因此必须重新求解。

D 应只把 `solve_required=True` 的候选交给 C；该字段是 A 的几何/输入去重结论，不表示候选一定改善。

## 5. 栅格与 NPZ 约定

### 5.1 坐标和单位

- 原点：场地左下角 `(0,0)`。
- x 向右，y 向上；单位为米。
- A-local v0.2 使用方形栅格：`resolution` 米/格，`Nx=round(L/res)`，`Ny=round(H/res)`。
- 数组形状为 `(Ny,Nx)`，即 `[iy][ix]`。
- 格心坐标为 `((ix+0.5)*res, (iy+0.5)*res)`。
- 旋转矩形采用格心采样，格心落在设施内（含边界）即不可通行。
- `rho0` 单位为 `person/m2`，总人数为 `sum(rho0)*res*res`。
- `walkable=False` 的格子不分配初始人群。
- A 不生成速度场、时间帧或速度矢量；这些由 C 定义和输出。

### 5.2 NPZ 字段

| 字段 | 类型/内容 |
| --- | --- |
| `rho0` | `float32 (Ny,Nx)`，初始密度 |
| `walkable` | `bool (Ny,Nx)`，最终可行走掩码 |
| `base_walkable` | `bool (Ny,Nx)`，不含参数化设施 |
| `obstacle_mask` | `bool (Ny,Nx)`，固定障碍+设施 |
| `fixed_obstacle_mask` | `bool (Ny,Nx)` |
| `facility_mask` | `bool (Ny,Nx)` |
| `zone_id` | `int32 (Ny,Nx)`，-1 表示无人群区 |
| `dx` | 标量，栅格分辨率，米 |
| `exits_grid` | `float32 (n,4)`，每行 `[x1,y1,x2,y2]`，出口 ID 按 `exit_ids` 排序 |
| `exit_ids` | 出口 ID 数组 |
| `exit_cells_json` | JSON 字符串，出口 ID 到 `[ix,iy]` 列表 |
| `params` | JSON 字符串，含 `walk_speed`、`T`、可选 `dt` / `jam_density` |
| `scene_json` | JSON 字符串，完整场景 |
| `scene_version` / `scene_revision` | 本地版本和修订号 |
| `layout_json` | JSON 字符串，设施位姿 |
| `layout_policy_json` | JSON 字符串，几何约束阈值 |
| `variable_parameters_json` | JSON 字符串，给 B 的参数声明 |
| `mask_hash` / `walkable_hash` / `input_hash` / `layout_hash` | SHA-256 字符串 |
| `crowd_covered_cells` | 标量，设施压住的人群格数；合法导出应为 0 |

C 必须根据新场景重新构建路径规划、碰撞或边界处理，不能只接收连续位姿而忽略掩码变化。A 的 `input_hash` 可用于记录和核对，但不能证明 C 已经真实执行求解。

## 6. 对 D 首轮清单的逐项回复

### 6.1 A：设计变量与约束

1. **出口首版支持宽度、位置、数量中的哪些？**  
   候选接口只支持已有出口的宽度。位置和数量可在场景编辑器中作为结构编辑，但不是当前 D 候选变量。
2. **通道是否支持宽度、位置、连通？**  
   可用墙体和障碍表达通道，A 检查人群到出口的连通与近似最小宽度；不支持独立通道宽度/位置/连通变量。
3. **可移动设施支持哪些参数？**  
   支持中心 x/y、旋转角；权限允许时也支持长宽。第一版建议固定尺寸、仅移动/旋转、`effect="block"`。
4. **ID、当前值、单位和范围是否齐全？**  
   场景中有稳定 ID；`variable_parameters` 提供展示名、类型、目标、单位、范围和当前值。没有声明的对象仍受自身权限和几何规则约束。
5. **连续还是离散？**  
   当前是连续数值，旋转会归一化；没有自动步进或吸附到栅格。D 可自行选择采样步长，但不应把视觉位移等同于有效计算变化。
6. **允许区域和联合约束是否支持？**  
   支持设施完整 contained-in 允许区域、尺寸范围、不重叠、不穿墙、不压人群、出口净距和必要通路约束；没有通用任意联合约束表达式。
7. **D 直接改 JSON 还是调用 A 函数？**  
   推荐调用 `apply_layout()` / `evaluate_candidates()`。直接改 JSON 会绕过权限、声明刷新、修订号和范围检查。
8. **能否生成新场景并保留基线？**  
   可以。深拷贝生成新场景并递增修订，原场景不变；批量报告保留基准哈希和每个候选的变化。
9. **有哪些校验和失败原因？**  
   包括对象未知、越权、字段非法、超界、重叠、穿墙、压出口、压人群、不可达、通路过窄、栅格不可见、参数声明错误等，统一返回 `{level,msg}`。

### 6.2 C：格式、计算与公平比较

1. **哪些建筑变化真正影响求解？**  
   改变 `walkable`、`obstacle_mask` 或出口几何的变化会进入 A 的求解输入。C 必须消费这些变化；仅 `layout_hash` 改变而输入哈希不变不构成新 PDE 输入。
2. **如何处理网格等效候选和最小有效移动？**  
   A 提供 `mask_changed`、`below_grid_resolution`、`duplicate_mask_of`，批量以 `input_hash` 去重。A 不承诺存在统一的“最小有效移动米数”，它取决于姿态、尺寸和栅格。
3. **密度/速度、网格、原点、轴、时间和存储由谁定？**  
   A 已确定密度、网格、原点、轴、初始场景和 NPZ；速度和输出帧格式、采样 cadence、大数组正式存储由 C 提出并与 B/E 确认。
4. **指标需要哪些输入？**  
   A 提供初始密度、总人数、可行走掩码、出口线段和出口格。有效面积密度、出口流量积分和热点定义由 D/C 确认，A 不替 D 定义。
5. **公平比较、种子、运行时间和失败检测由谁负责？**  
   A 保证除提交的修改外深拷贝基线，并记录输入哈希和修订。种子策略、求解配置、运行元数据、耗时和失败分类由 C/E；指标与排序由 D。
6. **FNO 是否为 D 的前置条件？**  
   不是。D 可先用 A 的几何报告和 Mock 数据准备，最终候选评价仍需要真实 PDE；A 不默认当前 FNO 支持任意障碍布局。

### 6.3 B：读取与展示

1. **B 现在能读什么？**  
   可读 `scene_json`、`layout_json`、`variable_parameters_json`、设施位姿、参数前后差值和 A 的预览/场景数据。
2. **场景、场和分析是否分开？**  
   应分开。A 提供场景；C 提供密度/速度场和轨迹（如有）；D 提供指标/热点/比较结论。B 不读取一个混合对象后自行重算核心结果。
3. **整体指标、时间序列、热点和比较记录由谁提供？**  
   D 负责指标和热点，C 负责时间场，E 负责持久化关联，B 负责展示。A 只提供场景、参数和几何变化。
4. **热点坐标、时间轴和职责如何对齐？**  
   A 的格坐标是 `[ix,iy]`，原点左下角。热点若用格坐标必须带 `ix/iy`；时间轴必须使用 C 的 `time_s`，不能把数组下标直接当秒。
5. **来源/状态/失败信息如何展示？**  
   B 应显示 C 的结果来源（mock/pde/fno）和 E 的任务状态/失败原因。A 不把导出的 NPZ 或合法几何标记成“PDE 已成功”。

## 7. 对设施优化提案的结论

| 提案 | A 当前结论 |
| --- | --- |
| 首版使用固定尺寸、不可穿越矩形展台 | 支持，推荐这样限定首轮范围 |
| 服务点、排队、降速区后续再做 | 同意，当前明确不支持 |
| A 参数化设施并校验几何 | 已实现 |
| D 生成位置/朝向并比较指标和移动代价 | D 负责；A 提供原始位移/旋转，不负责排序 |
| C 将移动设施转成掩码并重算 | A 已输出新掩码和输入哈希；C 的实际消费仍待联调 |
| 初始人群区作为禁放区 | 已实现为 error |
| D 跳过网格等效掩码 | A 已提供去重结果 |
| 不假设 FNO 支持任意障碍 | 同意，须由 C 验证适用范围 |

## 8. 建议对接顺序与验收条件

1. A/C/D 先确认首轮变量：建议 `exit_width` + 固定尺寸设施 `center`/`rotation_deg`。
2. C 用 `gym_facilities_example.json` 和一个候选 NPZ 做最小真实求解，证明新掩码进入路径/碰撞/边界处理。
3. D 对同一组候选确认指标输入、出口流量定义、代价字段和 `solve_required` 用法。
4. B 用同一基准/候选读取场景和参数差值，等待 C 的真实场与 D 的分析结果。
5. E 再接入场景保存、任务执行、结果关联和失败状态。
6. 联合评审通过后，才把必要的 v0.2 字段升级到共享契约，并同步 Schema、样例、语义检查和消费方。

A 本地交付完成的标准不是“文件已生成”，而是消费方实际读取并完成以下证据：

- 基准与至少一个合法候选可重复加载、导出并核对修订和哈希；
- 非法候选被拒绝且显示具体原因；
- C 证明设施/出口变化进入真实求解输入；
- D 保留合法、非法、重复和无改善候选；
- B 正确显示参数变化、坐标、时间和来源；
- E 能保存并重新打开完整运行记录。

## 9. 已知限制与非目标

- 共享 CrowdTurb 契约仍为 0.1.0；本文件的 v0.2 只在 A 本地生效。
- 通道尚无独立参数化，出口候选仅宽度可调。
- 设施仅支持不可穿越旋转矩形；服务点、排队、降速区和非矩形设施不在本版。
- 编辑器允许区域精修仍不完整，复杂多边形需要在 JSON 中完善。
- 最小通路宽度是 8 邻域离散近似，不是精确工程净空。
- 极薄设施可能不占栅格；小幅移动可能不改变掩码。
- A 不验证 PDE 方程、稳定性、质量守恒、速度场、FNO 精度或实时性能。
- A 的 `metrics` 只是几何格数统计，不是 D 的拥堵指标。
- A 不定义任务 API、数据库、运行状态或结果存储。
- 本模块结果不能作为真实疏散安全认证结论。
